## 2026-11-17 第三步：动作连接重置（本地修改完成，未部署）

关联的旧任务，记录 `CANCELLED / COMMAND_CONNECTION_LOST`，释放对应占用。
可能已发送的动作保留未知结果，迟到回报只补历史，不续做旧计划。语音连接单独断开不调用此流程。

旧连接注销晚于新连接接入的情况。其他机器人及未分配任务不受影响。

### 当前平台消息

- `pcm_segment`：完整句通知，保留录音诊断字段，补上上传端提供的 `capture_id`。
  当 `end_reason=silence` 时，机器人据此停传、清掉计时。带编号的一轮仅受理第一句；
  该编号后续已在网络途中的 PCM 丢弃，下一次恢复上传必须使用新编号，避免重复建任务。
  不带编号的整段/旧 PCM 入口继续受理合法输入；不增加上传前授权握手。
- `pcm_task`：受理回执，含 `task_id`、`turn_id`、版本、录音编号和收音编号（若有）。
  它不是结束通知，不能据此恢复收音。
- `task_state`：同一执行轮次的当前状态，例如规划、执行、等待批准或澄清。不是结束。
- `done`：仅在 `REPLIED` 时作为文字回复结束通知；带 `kind=reply`、回复原文、
  `playback=none`、`play_secs=0` 及任务/执行/录音/收音关联信息。当前没有配置 TTS，
  不等待声音，也不把未配置 TTS 当错误。已有可选 TTS 适配器不作为当前验收前提。
- `task_finished`：状态为 `SUCCEEDED`、`COMPLETED_WITH_SKIPS`、`FAILED`、`CANCELLED`，
  或持久记录明确 `advancement_stopped=true` 时发送。后者包含已停止推进的 `BLOCKED`。
  保留原状态、错误和结果争议信息，不把失败/未知改成成功，不表示物理动作已停止。
- `state:error`：保留错误，输入阶段标注 `phase=voice_input`，查任务状态失败标注
  `phase=task_notification`；后者不会伪造结束消息。

平台不再发送语音 `idle` 或用于延长收音窗口的 `pcm_activity`。
任务交互记录中的 `interaction.phase=idle` 是另一套字段，保持原样。

### 通知来源和生命周期

任务受理回执发送后，在该连接存活且任务未结束时，每 250 毫秒通过 TaskService
读取同一个 `task_id/turn_id` 的已提交记录；首次读取立即进行。版本未改变不重复通知。
采用读取已有记录的方式，是为了覆盖后台模型直接回复、规划失败、取消、停止推进和
动作回报等全部入口，避免只监听机器人动作回报而漏掉纯文字回复。
这会有最多一个轮询间隔加数据库/网络耗时的通知延迟，并非数据库提交时同步发送。

读取使用现有客户、可见性及会话归属检查，不跟随同一会话中新建的下一轮。
通知只投影持久事实，不修改任务、动作结果或占用。状态读取失败只报告错误并等待恢复；
不得推断任务结束。连接关闭/被替换、服务关闭时取消该连接的通知工作。
WebSocket 输入回执和后台任务通知通过同一个发送锁写入，受理回执先于结果通知。

整段 WAV 的 WebSocket、HTTP 流式入口也删除 `idle`，使用同样的实际任务结果通知。
HTTP 流在任务未结束时继续等待；等待人工处理时也不会伪造 `done`。
历史平台唤醒评估模式仍返回 `pcm_wake`，只删其 `idle` 收尾，不将评估结果冒充任务结果。

## 交互与职责

1. 机器人等待唤醒时只在本地检测，不上传环境 PCM。
2. 检测到“小千小千”后播放本地“我在”。播完并经过回声保护，直接上传 PCM。
   没有 voice_hello、voice_ready、wake、wake_state、wake_end，没有等待确认的一秒缓存。
3. 平台沿用已有 VAD 切句、转写、输入落表、任务受理、规划及执行链路。
4. 机器人开始上传时启动本地无人声计时，speech_timeout_secs 默认 10 秒。
   平台检测到有效人声时反馈事实，机器人收到本轮反馈则续期；静音不会续期。
   反馈缺失也按本地计时停传，因此旧平台缺少反馈时不能保证超过初始时长的连续收音。
5. 平台处理语音、机器人播放声音时，仍暂停麦克风处理。处理结束后若计时已经过期，
   机器人回到等待唤醒；不会撤销平台已经接收的任务。
6. 断线清掉本轮机器人状态，重连后重新唤醒。平台始终可以处理新的合法 PCM，
   不以本地计时是否到期作为接收或任务受理的门槛。

第一版为半双工：先呼叫，等“我在”及回声保护结束后再说任务，不承诺唤醒词和指令连说不丢字。

## 平台部署配置

部署本功能时，最终合并的配置需要设置：

```json
"voice_pcm": {
  "enabled": true,
  "evaluate_wake": false,
  "submit_tasks": true
}
```

保留 wav_save_dir 等其他字段。使用已有的直接 PCM 处理路径，不新增允许上传的握手开关。
不再使用之前草案中的 allow_local_wake。evaluate_wake=false 让平台不再从转写文本寻找唤醒词。
当前项目正式启动配置在 application_overrides.voice_pcm 中覆盖业务配置，部署时需同步把
该覆盖对象的 evaluate_wake 改为 false；只改被覆盖的底层文件不会生效。

## 音频分组与人声反馈

机器人沿用 audio / pcm_b64 帧，额外携带 UUID 格式的 capture_id，表示本轮收音。
这个字段是分组信息，不是唤醒凭证或权限。平台收到不同编号的第一帧时，
清掉上一轮未完成的切句缓存，再立即处理当前 PCM；没有预登记或确认等待。
同一连接没有编号的旧客户端继续走原有连续流路径。

平台从已有 SpeechActivity 事件确定有效人声，仅对带编号的 PCM 最多每 0.5 秒反馈一次：

```json
{"type": "pcm_activity", "capture_id": "本轮 UUID", "speech": true}
```

机器人只在正在上传且编号匹配时更新本地计时。旧轮次的迟到反馈不能续期新轮。
平台不会因为没有该反馈而拒绝后续 PCM。连接身份、数据格式与大小、任务执行权限仍按原规则检查。

## 每个计划一次确认播报

平台命令帧携带 plan_id。机器人动作执行模块正常受理后通知语音节点，
在启用标记存在且该计划尚未记录播放尝试时，播放本地“好的，开始执行”。
先持久记录尝试，再入播放队列；后续步骤和重启不重播同一计划。
拒绝、取消或迟到受理不触发确认；播报失败记错，不改变动作结果。
播放与动作执行并行，不等待播报结束才移动；播放尝试记录不等于实际听音成功。

模型、本机 voice.json、audio/plan_ack.enabled 和 audio/plan_ack.sqlite3 在机器人数据目录，
不进 Git。两段通用录音随语音 Python 包和 Git 发布。
